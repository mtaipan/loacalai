# Возможности агентных систем и разрыв Local Gemma Studio

Дата проверки: 1 ноября 2026. Основание: пользователь считает агент слабым и просит исследовать Claude, ChatGPT/Codex и другие системы. Это исследование официальной документации и сопоставление с текущим кодом, не сравнительный прогон продуктов. Наличие документированной функции не гарантирует правильность каждого её выполнения. Облачная/desktop/CLI/IDE-функциональность, плагины и preview могут различаться.

Основной план исполнения: [DEVELOPMENT-PLAN.md](DEVELOPMENT-PLAN.md), R12. Источники описывают возможности продуктов; оценки нашего проекта и проектные рекомендации ниже — наши выводы. Код приложения не менялся.

## Что умеют другие системы

### Claude Code

Документация описывает цикл получения контекста, действия и проверки, инструменты файлов, поиска, shell, веба и Git. Среда позволяет запускать тесты и серверы, изучать ошибки и корректировать решение. Поддержка определений/ссылок/диагностик кода подключается через code intelligence plugins. Это отдельная интеграция, а не способность любого текстового поиска понимать символы. [Как устроен Claude Code](https://code.claude.com/docs/en/how-claude-code-works), [Code intelligence](https://code.claude.com/docs/en/plugins/code-intelligence).

Сохраняются сессии с сообщениями и инструментальными результатами, доступны resume/fork и snapshots изменяемых файлов; есть автоматическое сжатие контекста и инструкции проекта. Это помогает продолжению, но не делает контекст бесконечным и не гарантирует сохранение каждой детали сжатия. [Сессии и контекст](https://code.claude.com/docs/en/how-claude-code-works).

Subagents выполняют специализированные подзадачи в собственных контекстных окнах с определёнными инструментами/правами и возвращают результат. Это отличается от одного вызова модели с просьбой дать совет. Есть разделение работы в foreground/background. [Subagents](https://code.claude.com/docs/en/sub-agents).

Расширения включают навыки, MCP и hooks; hooks работают на событиях жизненного цикла, включая вызовы инструментов и завершение. Подключённый hook может выполнять конкретную проверку вместо надежды, что модель вспомнит инструкцию. Сам по себе hook не доказывает корректность проверки. [Hooks](https://code.claude.com/docs/en/hooks).

### Codex и ChatGPT

Не смешивать Codex coding workflows и возможности обычного ChatGPT-чата. В официальной документации есть самостоятельные разделы про терминал, обзор изменений, подключение MCP, навыки/плагины, subagents и worktrees. Возможности конкретной поверхности и среды нужно сверять отдельно. [Integrated terminal](https://learn.chatgpt.com/docs/integrated-terminal), [MCP](https://learn.chatgpt.com/docs/extend/mcp), [Skills & Plugins](https://learn.chatgpt.com/docs/skills-and-plugins).

Worktrees дают раздельные checkout для параллельной работы; subagents — делегирование задач. Наличие нескольких агентов не означает безопасную одновременную правку одной рабочей копии и не делает каждую задачу быстрее. [Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees), [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Длительная работа представлена через цель, ограничения и критерии завершения; можно направлять работу последующими сообщениями, получать состояние, приостанавливать и продолжать. Полезный принцип для нашего продукта — сохраняемая цель с проверкой результата, которая живёт дольше отдельного ответа модели. [Long-running work](https://learn.chatgpt.com/docs/long-running-work).

Права и sandbox различаются: решение не спрашивать перед каждым действием само по себе не создаёт изоляцию команд. Для нашего проекта это уже учтено в R01/DEC-03. [Sandbox](https://learn.chatgpt.com/docs/sandboxing).

### Cursor

Agent ищет по проекту и вебу, редактирует файлы, выполняет shell-команды; Plan Mode предназначен для подготовки плана до исполнения. Документация Agent прямо указывает отсутствие ограничения количества tool calls на задачу; это не утверждение об отсутствии внешних квот сервиса или физических ограничений. [Agent overview](https://cursor.com/docs/agent/overview), [Plan Mode](https://cursor.com/docs/agent/plan-mode).

Для нашего приложения важны раздельные исследование/план/исполнение, работа с контекстом проекта и обратная связь от инструментов. Копировать внешний вид IDE или рекламную формулировку «понимает весь проект» недостаточно.

### Gemini CLI

Официальный набор инструментов включает файловые операции, shell, web и другие специализированные действия. Постоянная память различает общие инструкции проекта, частные заметки проекта и межпроектные предпочтения. Это полезнее бесконтрольного подкладывания полного старого диалога. [Tools reference](https://geminicli.com/docs/reference/tools/), [Memory files](https://geminicli.com/docs/tools/memory/).

Checkpointing сохраняет состояние проекта и сведения о диалоге/инструментах перед изменениями для восстановления. Граница snapshot должна быть явной; нельзя обещать откат отправленного письма или произвольного внешнего эффекта по аналогии с откатом файла. [Checkpointing](https://geminicli.com/docs/cli/checkpointing/).

### GitHub Copilot

Документация описывает связанный поток задач: контекст репозитория/issue/PR, планирование и агентная работа, обзор изменений; различает клиент, сохраняемую сессию и окружение исполнения. Для нас полезен законченный путь от задачи до проверяемых изменений, а не только генерация файлов. Облачное окружение GitHub и локальная работа нашего приложения не тождественны. [Copilot in the cloud](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent).

## Что уже есть у нас и чего не хватает

Сверка: `src/tools.rs` — реальные определения инструментов; `src/agent.rs::plan` — устройство плана; `src/projects.rs` — обзор проекта; `src/specialists.rs` — протокол консультации; `src/engine.rs` — управляющий цикл. «Отсутствует отдельный механизм» ниже не означает, что невозможно разово выполнить аналогичное действие через произвольную shell-команду.

| Способность | Текущее состояние | Вывод для проектирования |
|---|---|---|
| Читать/искать/изменять файлы | Есть инструменты, literal search, backup и проверка записи | Основа уже существует; нужны полные материалы, диапазоны/форматы, batch changes и recovery |
| Ориентироваться в кодовой базе | inspect_project даёт ограниченное дерево/manifest, search_files ищет текст | Добавить индекс и карту проекта; semantic retrieval не заменяет definitions/references/diagnostics |
| Держать цель и план | update_plan возвращает JSON модели, до 8 шагов; это не долговечный управляющий граф задачи | Сохраняемые требования, этапы/зависимости, evidence, незавершённые пункты, актуализация после ошибок |
| Долго исполнять задачу | Цикл инструментов есть; обнаружены task/HTTP caps и проблемы продолжения | R09/R10: работа между контекстными окнами, отсутствие общих обязательных квот, ресурсы и resume |
| Терминал/серверы | run_command захватывает вывод; schema запрещает persistent servers, default/cap 120/900 с | Нужны управляемые process sessions, polling/log ranges/stdin при поддержке, сервер health/ports и stop дерева |
| Git workflow | Отдельный git_info только status/diff/log; изменения Git возможны через shell | Структурированное состояние branch/worktree/diff/conflicts, сохранение чужих изменений, проверяемый итог; внешняя публикация только по задаче пользователя |
| Исправлять ошибки по проверкам | Можно запускать команды; completion checks частично эвристические | Verification pipeline по критериям задачи, типизированный результат и цикл исправления; не просто фраза «запусти тесты» |
| Проверять приложение в браузере | Есть browser refs/actions/screenshots | Нужны managed dev server + реальные проверки UI + наблюдения результата; screenshot не равен визуальному пониманию OCR-моделью |
| Память | Есть история и корневой AGENTS.md; известны потери retry/URL и ограничения контекста | Hierarchical project instructions, сохраняемые facts/decisions и отбор памяти по релевантности без выдачи источнику прав |
| Настоящее делегирование | Team формирует консультацию Foundation-Sec по последним успешным наблюдениям | Это полезная консультация, но не универсальная команда исполнителей с отдельными планами/контекстами и join/cancel |
| Внешние инструменты | Встроенный фиксированный набор | Нужен расширяемый registry, capability discovery; MCP adapter как отдельное подключение по выбору пользователя |
| Повторяемые навыки | Инструкции приложения и проекта | Нужны пакеты workflow с описанием, ресурсами и проверками, загружаемые по задаче, а не все в каждый prompt |
| Детерминированные проверки | Есть отдельные программные guards и fixtures | Нужен событийный pipeline validators/hooks, который не может быть обойдён красивым ответом модели |
| Результат для человека | Карточки действий, текст, частичные diff/backup | Review набора изменений, результаты проверок, артефакты и оставшиеся требования, переход к файлу/источнику |
| Управление в процессе | Есть stream и stop; reload теряет связь | Сохраняемые run/events и пользовательские уточнения, не создающие второй конкурентный run |

## Почему агент может казаться «тупым»

Это несколько независимых причин, а не одна оценка модели:

1. **Возможность не передана:** intent heuristic выключает tools, URL отключает проектные возможности, инструмент не умеет управлять сервером. Даже сильная модель не выполнит недоступное действие.
2. **Не тот материал:** кусок дерева/первые символы/потерянное вложение, старые наблюдения, отсутствие нужного контекста. Модель отвечает по неполному состоянию.
3. **Слабый управляющий цикл:** короткий текстовый план, отсутствие сохранённых критериев и автоматического возврата от failed checks к исправлению.
4. **Нарушенная непрерывность:** timeout/reload/повтор меняют историю или заставляют начинать заново, а не продолжать проверенное состояние.
5. **Перегрузка устройства:** слишком большой контекст, prefill и удержанные ресурсы. Долгое молчание/зависание нельзя лечить только увеличением deadline.
6. **Ограничение модели:** ошибки рассуждения, tool arguments, работы с большим кодом, следования источникам. Это остаётся даже при правильной оболочке и требует реального сравнения весов.

Название «30B» не равно гарантированному уровню Claude/Codex, а Q4/abliteration сами по себе не доказывают ни слабость, ни качество. Оценивается конкретный checkpoint+quantization+template+runtime+инструменты на повторяемых задачах. Более сильная модель и более надёжное приложение — две отдельные оси улучшения.

## Рекомендуемая целевая система

Рабочий цикл: **цель/требования → сбор контекста → план → действие → наблюдение → проверка → исправление либо следующий этап → проверяемое завершение**. Пользовательское уточнение обновляет сохраняемую цель. Полные артефакты остаются на диске; контекст модели содержит только нужное текущему этапу. Цикл не ограничен одним окном модели или обязательным числом действий.

Первая необходимость уже покрыта A–M и R01…R11: надёжные задачи/ресурсы, контекст, права, поиск, материалы, проверки и восстановление. Новые конкретные предложения по результатам сравнения: managed terminal/dev servers, hierarchical instructions, skills/tool registry/MCP, code intelligence, управление уточнениями и опциональное изолированное делегирование. Они описаны в R12 основного плана со статусом проектных предложений, без утверждения, что пользователь заказал копию каждого конкурирующего продукта.

Не начинать с десятка одновременно загруженных моделей. Для локального профиля сначала один качественно управляемый исполнитель. Логические роли планировщика/исполнителя/проверяющего могут исполняться последовательно одним LLM; программные проверки и tool evidence независимы от его самооценки. Делегирование даёт пользу только при понятной декомпозиции, владении файлами, ресурсах и сведении результатов.

Критерий усиления агента — задача проходит сквозной сценарий с настоящим результатом, а не увеличилось число инструментов/моделей/строк промпта. Обязательны неизвестный заранее fixture-проект, баг с воспроизведением, многофайловое изменение, запуск UI, ошибочный тест, рестарт/продолжение и честный непроверенный остаток. Сравнение моделей проводится отдельно от тестов инфраструктуры.
