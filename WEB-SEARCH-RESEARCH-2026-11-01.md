# Как устроен поиск в AI-сервисах: материалы для разработки

Дата проверки источников: 1 ноября 2026. Цель — определить применимые архитектурные решения для Local Gemma Studio. Это изучение официальных публикаций, а не независимый аудит закрытых сервисов или сравнительный тест качества.

Нужно различать пользовательский продукт, его быстрый поиск, режим Research и публичный API. Описание одного режима/API не доказывает одинаковую реализацию всех остальных. Результаты и заявления производителей о превосходстве не принимаются за независимые измерения.

## Что опубликовано

### Perplexity

В инженерном описании Search API компания раскрывает собственную инфраструктуру индексации и комбинированный поиск: кандидаты по словам и смыслу объединяются, проходят фильтры и несколько стадий ранжирования, включая cross-encoder. Извлечение и ранжирование работают с документами и отдельными фрагментами. Важна свежесть индекса. Это значительно больше, чем получение готовой HTML-выдачи стороннего поисковика. [Архитектура Search API, 25 сентября 2025](https://www.perplexity.ai/en-GB/hub/blog/architecting-and-evaluating-an-ai-first-search-api).

Отдельная публикация описывает улучшение извлечения: оценку необходимых, нерелевантных и повторяющихся фрагментов документа относительно запроса. Оптимизируются полнота полезной информации и компактность контекста. [Better Extraction, Dynamic Benchmarks](https://www.perplexity.ai/en-GB/hub/blog/search-api-better-extraction-dynamic-benchmarks).

В опубликованной архитектуре Search as Code модель составляет поисковый процесс программно: retrieval, ranking, filtering, параллельные ветви, rendering. Код выполняется в sandbox; промежуточные данные можно обрабатывать до включения полезного результата в контекст. Это описанный компанией подход к агентному поиску, не основание считать каждый обычный запрос многотысячным исследованием. [Search as Code](https://www.perplexity.ai/en-GB/hub/blog/rethinking-search-as-code-generation).

### ChatGPT / OpenAI

Официальная API-документация различает быстрый поиск, агентный поиск reasoning-модели с решениями о продолжении и Deep Research. Доступные действия включают поиск, открытие страницы и поиск внутри страницы. Ответ содержит структурированные аннотации цитат с URL, названием и позицией в тексте. Этот интерфейс показывает наблюдаемые действия и цитирование; он не раскрывает полный внутренний поиск пользовательского ChatGPT, всех поставщиков данных или формулу ранжирования. [Web search](https://developers.openai.com/api/docs/guides/tools-web-search).

### Claude / Anthropic

Web Search позволяет модели запускать повторные поиски в рамках запроса. В документации описаны ограничения числа вызовов и доменов, цитаты, а в новых вариантах инструмента — dynamic filtering: модель обрабатывает результаты кодом, чтобы в контекст попадала релевантная информация. Это возможности конкретного API, а не доказательство одной внутренней архитектуры всех режимов Claude. [Web search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool).

В инженерном разборе Research от июня 2025 описаны ведущий агент, план исследования, параллельные исследователи, повторные циклы по мере нахождения информации, сохранение состояния и отдельный CitationAgent, который подбирает места источников для ссылок. Публикация также обсуждает сложность, расход ресурсов, надёжность и необходимость оценки. Не следует приписывать такую многоагентную схему каждому обычному веб-поиску Claude. [Multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system).

### Gemini и Google Search AI Mode

В Gemini API Google Search grounding модель определяет полезность поиска, генерирует один или несколько запросов, обрабатывает найденное и возвращает ответ с аннотациями источников и данными поисковых вызовов. [Grounding with Google Search](https://ai.google.dev/gemini-api/docs/google-search).

Google отдельно описывает query fan-out для AI Mode/AI Overviews: несколько связанных поисков по подтемам и источникам данных. Режимы могут использовать разные модели и техники. Gemini API, AI Mode и Deep Research нельзя автоматически считать одной реализацией. [AI Features and Your Website](https://developers.google.com/search/docs/appearance/ai-features).

### Grok / xAI

API предоставляет Web Search для поиска и чтения веб-страниц, включая ограничения по доменам. [Web Search](https://docs.x.ai/developers/tools/web-search).

X Search — отдельный инструмент с поиском по словам, смыслу, пользователям и чтением треда, с источниками результата. Это пример полезности специальных источников вместо попытки искать все виды данных одной веб-выдачей. [X Search](https://docs.x.ai/developers/tools/x-search).

## Выводы для Local Gemma Studio

Это предлагаемые решения для нашего продукта, а не утверждение, что каждый перечисленный сервис реализует каждый пункт одинаково.

1. **Отделить вопрос от поисковых запросов.** Сохранить исходное намерение и контекст, выделить факты для проверки, сформировать короткие запросы. Не передавать автоматически всё сообщение с кодом/вложениями поисковику.
2. **Разделить быстрый поиск и исследование механизмом исполнения.** Быстрый поиск должен иметь небольшой бюджет; исследование — план подтем, итерации, проверку пробелов и условия остановки. Одна инструкция «прочитай три сайта» не является полным механизмом.
3. **Делать несколько независимых поисков при необходимости.** Подтемы, даты, названия продуктов, первичные документы; параллельность с ограничением ресурсов. Несколько HTTP-запросов не требуют нескольких одновременно загруженных LLM.
4. **Улучшить слой получения результатов.** Общий интерфейс поставщиков, понятные ошибки/ограничения, даты, фильтры, резервные источники и кеш. Платные API рассматриваются как опции, а не как обязательная покупка или замена локальной модели.
5. **Отбирать фрагменты относительно вопроса.** Сохранить структуру статьи, заголовки, таблицы и происхождение; исключать меню, дубли и нерелевантный текст. Не ограничиваться первыми N символами страницы. Реранкер должен помогать отбору материала, а не только менять порядок нескольких сниппетов.
6. **Вести реестр источников и доказательств.** Что найдено, что действительно прочитано, какой диапазон, когда, с каким HTTP-статусом и ограничением; какие утверждения поддерживаются какими фрагментами.
7. **Сопоставлять утверждения с источниками.** Программно проверять существование источника/фрагмента и доступность материала; смысловую поддержку утверждения оценивать отдельно. Наличие ссылки не гарантирует истинность, а добавление CitationAgent само по себе не решает проблему.
8. **Допоиск по пробелам и противоречиям.** Отслеживать покрытие вопроса, зависимость источников, первичные публикации и даты. Не приравнивать число доменов или количество запросов к качеству исследования.
9. **Показывать процесс и частичный результат.** Запросы, прочитанные источники, стадии, остановка, продолжение после перезагрузки; явная ошибка при недоступности поисковика. Не отвечать «ничего нет» по challenge/сбою парсинга.
10. **Сравнивать на одном наборе задач.** Проверять актуальность, полноту, соответствие ссылок утверждениям, русский/английский, недоступные страницы, пустую выдачу, задержку и расход ресурсов. Это важнее копирования фирменных названий режимов.

У нас уже есть цикл инструментов, fetch/browser, ссылки и попытка reranking. Основные недостающие части — планирование/контроль исследования, надёжное получение и отбор материала, восстановление состояния и проверяемая связь текста ответа с прочитанными фрагментами.

Для локального CPU разумно начать с одного управляющего LLM и ограниченно параллельной загрузки/обработки источников. Параллельные LLM-исследователи и исполнение сгенерированного моделью поискового кода — отдельные возможные расширения с измеряемой пользой и явной изоляцией, а не обязательный первый шаг.

Код приложения в рамках исследования не изменён. Подключения к платным API и установки новых компонентов не выполнялись.

### Надёжное восстановление и процессы

- Стандарт SSE определяет event ID и передачу Last-Event-ID при переподключении EventSource. Он сам не сохраняет события на сервере. Наш выбор: сохраняемый журнал + snapshot/cursor; при fetch-stream восстановление cursor реализуется явно, а не предполагается нативное поведение EventSource. [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html).
- Microsoft описывает наследование Job Object дочерними процессами, исключения breakaway и завершение при закрытии последнего handle с KILL_ON_JOB_CLOSE. Наш выбор: управляемая группа с момента старта до окончания потоков, в том числе после выхода родителя. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).
- Tokio поддерживает Unix process_group. Сам drop Child не заменяет гарантированный shutdown/reap. Наш выбор: сигналы группе и контролируемое завершение; группы не изолируют намеренно отделившийся daemon. [Tokio Command](https://docs.rs/tokio/latest/tokio/process/struct.Command.html).
- SQLite WAL позволяет согласованное чтение одновременно с записью, но имеет ограничения, включая локальный host и одного writer. Наш выбор: короткие транзакции, локальная БД, контроль checkpoint/занятости; large blobs отдельно. [WAL](https://www.sqlite.org/wal.html). Для согласованного backup предусмотрен официальный [Online Backup API](https://www.sqlite.org/backup.html). FTS5 даёт полнотекстовый поиск, а не смысловые embeddings: [FTS5](https://www.sqlite.org/fts5.html).
- Apple описывает маршрутизацию событий/действий через responder chain и NSPasteboard с changeCount. Это основание проверять native Edit menu, фокус и владение clipboard, но не доказательство найденной причины конкретного бага ⌘V. [Cocoa Event Architecture](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/EventArchitecture/EventArchitecture.html), [NSPasteboard](https://developer.apple.com/documentation/appkit/nspasteboard). Native-приёмка на Mac всё ещё не выполнена.

Ограничение получения документации: страница Ollama pull в веб-инструменте вернула только оболочку; Markdown endpoint — неподдержанный content type. Новое утверждение о её протоколе из этого чтения не делалось. Требование проверки terminal status и установленности уже обосновано локальным воспроизведением AUD-10; конкретный действующий протокол нужно проверить при реализации по установленной версии runtime.

Полное исследование не гарантирует заранее отсутствие новых дефектов. В основной план добавлены прослеживаемость, проверки переходов и правила пополнения требований, чтобы обнаруженные позже случаи попадали в общие механизмы и приёмку.

## Длительные агенты, память и ограничения: дополнительное исследование

Основание — новые сообщения пользователя о ненужных лимитах и зависании после «продолжай». Это расширяет исследование с поиска на устройство длительно работающего локального агента. Проверены официальные материалы; измерение текущего процесса и гипотезы записаны в R10 основного плана. Полное устройство всех нейросетевых систем этим чтением не исчерпано.

- Ollama документирует удержание модели через keep_alive, явную выгрузку, очередь и рост потребности в памяти при параллельных контекстах. Это позволяет различать здоровый warm cache, перегрузку и проблему очистки; таймер удержания не является пределом длительности задачи. [Ollama FAQ](https://docs.ollama.com/faq).
- Увеличение окна контекста повышает потребность в памяти. Наличие большого модельного окна не доказывает вместимость конкретного компьютера. Наш выбор — memory-aware context и checkpoints, а не автоматическая попытка использовать максимум. [Context length](https://docs.ollama.com/context-length).
- Anthropic описывает управление контекстом длительных агентов через compaction, структурированные заметки и подгрузку нужных материалов. Наш выбор — сохранять полную историю отдельно от небольшого актуального рабочего окна, продолжать задачу между окнами, удерживать требования и доказательства. [Effective context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents).
- Разбор long-running harness показывает отдельные проблемы передачи состояния, преждевременного «готово» и отсутствия сквозных проверок. Применяем сохраняемый список требований/прогресса, проверку фактического состояния и интеграционную приёмку. Это предложенная авторами архитектура, а не доказательство безошибочности любой модели. [Effective harnesses for long-running agents](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents).
- Документация llama.cpp server описывает runtime-настройки контекста/параллельности/пакетов и управление состоянием сервера; наличие флага само по себе не доказывает фактически занятую память. Параметры и доступность операций проверять по реально поставляемой версии. [Server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- PyTorch разъясняет различие живых выделений и свободного кеша allocator: empty_cache освобождает неиспользуемый кеш, а не живые tensors. Это иллюстрация необходимости диагностики слоя памяти, а не готовый рецепт для нашего llama/Ollama runtime. [empty_cache](https://docs.pytorch.org/docs/main/generated/torch.cuda.memory.empty_cache.html).

Изменение нашего решения по R09: обязательные task quotas времени/числа действий/страниц отменяются в проектировании. Физические границы одного inference, потоковая обработка данных, ограничения параллельности и диагностика неответившего endpoint сохраняют назначение — дать задаче работать долго без зависания ОС. Не смешивать эти механизмы в одном «лимите агента».
