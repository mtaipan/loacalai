# Windows installer publication contract

`Setup.cs` extracts the entire embedded payload into a unique sibling `.NAME.stage-UUID`. It validates normalized archive paths, duplicates, uncompressed size admission and SHA256 receipts. Payloads cannot contain `data` or prebuilt installation manifests. Offline `provision-windows.ps1 -VerifyOnly` runs against this private stage before publication; existing installation files and models are not used for this check. Changes to packaged files are rejected except the provisioning script's documented `runtime/python/python313._pth` regeneration. The final manifest inventories and hashes all staged component files.

`install-manifest.txt` identifies managed files from the previous installation. Its obsolete files remain in the retained previous version; unrelated files/directories, the entire data tree, model storage and optional non-payload modules are carried by same-volume rename. A preserved junction is moved as an entry, never traversed. A junction colliding with a new component is rejected. Model file identity is preserved; model weights are not copied into a second tree.

The per-root sibling `.NAME.update.lock` serializes installers. A Windows global named mutex, shared with `src/install_guard.rs`, serializes startup admission with commit/recovery. Its name is `Global\LocalGemmaStudio.Install.` plus UTF-8 SHA256 of the physical root path with ASCII letters uppercased and Windows separators. The installer does not hold this mutex while unpacking or verifying. Application startup obtains it before creating any data directories, checks the pending journal, then acquires its lifetime instance lease before releasing admission. Busy publication stops a launcher without opening data. An untouched old release may still start during staging; commit subsequently rejects its active lifetime lease.

The commit records its full carry plan with a flushed, atomically replaced sibling `.NAME.update.json`. After the idle lease and busy-file probes, it releases the file lease and renames the old root to a unique backup. Windows does not allow renaming its ancestor while a byte-range file lock is held. It carries preserved paths into the stage, checks component hashes again and publishes the complete stage by one directory rename. The root path is briefly absent between these operations. There is no promise of continuous path availability.

A unique `install-publication.txt` marker identifies publication. The complete directory rename is the irreversible commit point: a crash before the subsequent `committed` journal write still leaves the full new version. Recovery recognizes that marker and never rolls back first-launch data. Before publication, recovery restores carried entries and the old root; recovery itself can restart between every carry and the final restore rename. Interrupted carry/rename blocks application startup until the installer recovers. A legacy launcher without the startup guard can still recreate a root in the publication gap; recovery detects the conflicting root, preserves both copies and stops instead of merging or deleting new data.

Shortcuts/registry registration, WebView setup, optional model downloads and launch happen after commit. Their failure cannot roll back an already published version or overwrite data modified by its first launch. Offline dependency validation is not a physical GPU, UI launch or real model inference test. Backups, failed stages and private verification data remain available; this implementation performs no recursive deletion and has no automatic retention policy. An I/O failure during recovery reports the retained journal and paths rather than claiming successful rollback.

Run `runtime/python/python.exe scripts/tests/test_installer_transaction.py` for tiny isolated Windows fixtures. It compiles the real transaction with a console fixture entry point and invokes no GUI, provisioning script, user installation or actual application. The suite covers prepublication crash/restart, each carry/restore interruption, publication before/after the journal commit, first-launch data preservation, hash conflicts, verification failure, held instance and payload-file handles, ZIP64 insufficient-space admission, path/data/duplicate rejection, new installation, junction targets and publication mutex contention. No disk is filled and no models are downloaded. Rust `install_guard::tests` cover the matching identity and pending-journal admission without creating a data home.

`--extract-only` uses the same staged publication path but deliberately omits component provisioning, shortcuts, downloads and launch. Set `LOCAL_GEMMA_TEST_EXE` to a fresh Rust executable when running the fixture suite to also verify actual Rust startup against the C# mutex (including a non-ASCII root) and an interrupted journal, with no creation of a data home. Tests simulate process interruption, not power loss or failure of the storage controller to honor flush/rename durability.
